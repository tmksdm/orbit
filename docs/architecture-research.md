# Архитектурное исследование Orbit — выбор стека

- Дата: 2026-10-10
- Основание: поручение владельца (архитектурное исследование по результатам Stage 4)
  + дополнение владельца (local-first/offline-first, экспорт/импорт резервной копии).
- Статус: **исследование завершено, ожидает архитектурного решения владельца.**
  Миграция, экспорт/импорт и следующий Stage **не** выполнялись.
- Изолированные прототипы: `experiments/` (не входят в сборку, lint, typecheck, тесты).

Документ разделяет **подтверждённые факты**, **измерения**, **теоретические оценки**
и **ограничения**. Цифры приведены с источником; где измерение в песочнице
невозможно — это прямо указано, а не заменено оценкой из памяти.

## 1. Резюме (главный вывод)

1. **Зафиксированный «120 МБ» — это debug-универсальный preview-APK, а не размер
   поставляемого приложения.** По документации Expo release-APK SDK 50 ≈ 62 МБ,
   AAB ≈ 27 МБ, а размер загрузки из Google Play ≈ **11.7 МБ**; разница — это
   отсутствие R8/shrink, все ABI и dev-контур в debug-сборке. Значит, первый шаг —
   **не переписывание, а корректная release-сборка и её измерение.**
2. **Уведомление не пришло (FAIL Stage 4) — это дефект на уровне устройства/сборки,
   который нужно диагностировать до выводов о стеке.** Причину до диагностики
   фиксировать нельзя (см. §3, §10).
3. **Оптимизированный Expo/React Native (контрольный вариант) — рекомендуемый
   основной стек** для текущего продукта: он сохраняет утверждённые алгоритмы,
   тесты, дизайн и уже реализованный Stage 4, а размер приводится к «минимально
   оправданному» без переписывания.
4. **Если после оптимизации размер/надёжность всё ещё не устроят** и владелец
   отдельно разрешит переписывание — **Kotlin + Jetpack Compose** (или Kotlin +
   Android Views для абсолютного минимума). Обоснование: минимальный нативный
   прототип даёт release-APK **0.61 МБ** против debug **3.18 МБ** (§5.6).
5. **PWA отклоняется** для текущего объёма: локальные уведомления по расписанию
   без backend на основной платформе невозможны (Notification Triggers не
   поставляется, §5.2).
6. **Kotlin + Rust не оправдан:** доменная логика Orbit — простая календарная
   арифметика; Rust добавляет `.so` на каждый ABI, JNI-сложность и не даёт
   функционального выигрыша (§5.5).

## 2. Критерии выбора

Приоритеты владельца (не изменялись): функциональная полноценность, надёжность,
минимальный оправданный размер, быстродействие, экономное потребление ресурсов,
простота сопровождения. Размер не ограничен искусственно: 10 МБ предпочтительнее
20 МБ, 20 МБ предпочтительнее 120 МБ — **но только если меньший размер не требует
существенных функциональных компромиссов**.

Дополнение владельца (2026-10-10): local-first/offline-first; экспорт всех данных в
**один версионированный файл** с восстановлением; пользователь сам выбирает место
хранения (память телефона / облако через системное сохранение / меню «Поделиться»);
приватность, целостность копии, совместимость версий, корректное восстановление
напоминаний без дублирования; в перспективе — необязательные напоминания о копии;
автоматическая облачная синхронизация не предусматривается.

## 3. Подтверждённые факты Stage 4 (Android-проверка, фиксируются как есть)

Источник: итоги Android-проверки Stage 4 (сообщение владельца).

- Preview APK ≈ **120 МБ** — неприемлемый результат по ресурсоэффективности.
- Приложение устанавливается и запускается.
- Просроченный тестовый контакт отображается.
- Напоминания включены, время установлено на 20:00.
- **Уведомление не пришло, в том числе после повторного открытия приложения — FAIL.**
- Навигация по уведомлению — **NOT TESTED**.
- Системный статус-бар плохо читается: светлые значки на светлом фоне.
- Остальные непроведённые проверки — **NOT TESTED**.

**Предполагаемая причина отсутствия уведомления не устанавливается без
диагностики.** Возможные гипотезы (требуют проверки на устройстве, не выводы):
разрешение `POST_NOTIFICATIONS`/канал; режим энергосбережения (Doze/App Standby);
поведение inexact-alarm против exact; `expo-notifications` и перезагрузка
(`RECEIVE_BOOT_COMPLETED`); агрессивное энергосбережение производителя (OEM);
force-stop приложения; настройки системного времени. Диагностика — вне песочницы
(нет устройства).

## 4. Аудит текущего стека Expo / React Native

Стек (подтверждено `package.json`): Expo SDK 57, react-native 0.86.3, react 19.2.3,
TypeScript ~6.0, expo-router, expo-sqlite, expo-notifications, expo-image.

### 4.1. Измерения в песочнице (2026-10-10)

| Что измерено | Значение | Как получено |
|---|---|---|
| Android JS-бандл (Hermes bytecode) | **3 207 268 байт ≈ 3.2 МБ** | `npx expo export --platform android` |
| Полный экспорт Android (JS + шрифты + ресурсы) | **≈ 7.7 МБ** | тот же экспорт (каталог) |
| Шрифты Unbounded (9 начертаний) | ≈ 2.9 МБ (9 файлов 0.36–0.42 МБ) | вывод экспорта |
| `node_modules` (сборочный след, НЕ размер APK) | **≈ 827 МБ** | `du -sh node_modules` |
| Крупнейшие пакеты (сборочный след) | expo-image 135 МБ, expo-sqlite 76 МБ, hermes-compiler 47 МБ, react-native 39 МБ | `du` по пакетам |
| Состояние проекта | `npx expo-doctor` — **21/21** | запуск |

Ключевой вывод измерения: **сам JS-код Orbit мал (≈3.2 МБ bytecode)**; вес
release-приложения определяется нативной обвязкой RN/Hermes, ресурсами и —
критично — **конфигурацией сборки** (debug + все ABI + без R8).

### 4.2. Что формирует 120 МБ preview-APK

- **Debug-вариант** не минифицируется и не удаляет ресурсы (R8/shrinkResources off).
- **Универсальный APK** содержит **все ABI** (arm64, armeabi-v7a, x86, x86_64) —
  каждая архитектура несёт свою копию нативных библиотек RN/Hermes.
- **Dev/release-контур и ассеты** (шрифты всех начертаний, expo-image и пр.).
- По документации Expo: SDK 50 — release-APK 62.1 МБ, **AAB 27.4 МБ**, **Google Play
  11.7 МБ** [docs.expo.dev/distribution/app-size](https://docs.expo.dev/distribution/app-size/).
  Это примеры SDK 50, а не Orbit, но показывают масштаб влияния формата сборки.

> **Измерение невозможно в песочнице:** реальный размер release-APK/AAB/Play для
> *Orbit* здесь получить нельзя — нет устройства и контура подписи/Play. Ниже это
> отмечено в §10. Приведённые размеры Expo — из документации (факт документации,
> не измерение Orbit).

### 4.3. Веб-сборка текущего кода — FAIL

`npx expo export --platform web` **падает**: `node_modules/expo-sqlite/web/worker.ts`
импортирует `wa-sqlite/wa-sqlite.wasm`, которого в установленном пакете нет
(`None of these files exist: node_modules/expo-sqlite/web/wa-sqlite/wa-sqlite.wasm`).
Это значит: перевод текущего кода в PWA требует **отдельной работы** (другой
драйвер хранилища/сборка), а не «просто собрать web».

## 5. Исследование альтернатив

### 5.1. PWA без backend

- **Локальные уведомления по расписанию без backend невозможны** на основной
  платформе: Notification Triggers (`showTrigger`/`TimestampTrigger`) — статус
  **Launch: Not started**, требуется включение флага; Push API требует сервер
  [developer.chrome.com/docs/web-platform/notification-triggers](https://developer.chrome.com/docs/web-platform/notification-triggers).
  Это прямо противоречит требованию Stage 4 (напоминания без backend и без
  постоянного открытия приложения).
- Хранилище локально возможно (IndexedDB/OPFS), экспорт — через File System Access
  API / скачивание / Web Share API. Однако браузер может **вытеснить** данные
  (storage eviction), а Chrome с 2025 г. автоматически **отзывает** разрешения
  уведомлений у неактивных сайтов (ограничение автономности).
- **Вердикт: отклоняется** для основного приложения (не закрывает ключевую функцию).

### 5.2. Нативный Android: Kotlin + Android Views

- Полный контроль над `AlarmManager` (неточные, но надёжные напоминания без
  разрешения exact-alarm: `setAndAllowWhileIdle`), `BOOT_COMPLETED` для
  восстановления после перезагрузки, локальная БД (Room/SQLite), экспорт через
  Storage Access Framework и меню «Поделиться».
- Наименьший размер, максимальная предсказуемость батареи.
- Стоимость: **полное переписывание** UI и повторная реализация доменной логики
  (утверждённые алгоритмы Stage 1–3 на TS переносятся, но не переиспользуются).

### 5.3. Kotlin + Jetpack Compose

- Те же системные возможности (AlarmManager/BOOT_COMPLETED/SAF/Room), современный
  декларативный UI, меньше кода (по данным Google — до 50% меньше кода UI).
- Размер: официальное сравнение на minified release APK (Sunflower):
  **Views-only 2 252 КБ → Compose-only 2 966 КБ** (Compose добавляет ≈0.7 МБ;
  Compose-only меньше, чем смешанный вариант, т.к. уходят AppCompat/ConstraintLayout)
  [developer.android.com/develop/ui/compose/migrate/compare-metrics](https://developer.android.com/develop/ui/compose/migrate/compare-metrics).
- Итог по размеру: ориентировочно **~2–3 МБ release** для сопоставимого приложения
  (по данным Google, не измерение Orbit).
- Стоимость: тоже переписывание.

### 5.4. Kotlin + Rust

- Rust даёт смысл для тяжёлых вычислений/криптографии. Домен Orbit — календарная
  арифметика и правила интервалов (единицы операций) — на Rust переносить **нечего**.
- Добавляет `.so` на каждый ABI (+размер), JNI-сложность и вторую систему сборки
  (cargo + Gradle), усложняя сопровождение.
- **Вердикт: не оправдан.**

### 5.5/5.6. Минимальные измеримые прототипы

Реализованы и измерены вне рабочей реализации (`experiments/`):

**`experiments/kotlin-views/`** — Kotlin + Android Views: экран, локальное хранение
(SharedPreferences), планирование напоминания (`setAndAllowWhileIdle` +
`BroadcastReceiver` + `BOOT_COMPLETED`). Собрано в песочнице (Android SDK 34,
build-tools 34.0.0, Gradle 8.7, R8/minify+shrink in release).

| Артефакт | Размер (байт) | Размер |
|---|---|---|
| `app-debug.apk` | 3 179 111 | ≈ 3.18 МБ / 3.03 МиБ |
| `app-release-unsigned.apk` (R8) | **612 256** | **≈ 0.61 МБ / 0.58 МиБ** |
| из него `classes.dex` | 583 328 | ≈ 0.58 МБ |
| из него `resources.arsc` | 163 944 | ≈ 0.16 МБ |

Вывод: **нативное приложение сопоставимого назначения укладывается в единицы
МБ, а минимальный вариант — доли МБ.** Разница debug↔release здесь тоже ~5× —
это подтверждает, что основной «вес» Expo-варианта в первую очередь задаётся
конфигурацией сборки и нативной обвязкой RN.

**`experiments/pwa/`** — PWA без backend: экран + `localStorage` + попытка
`showTrigger`/`TimestampTrigger`. Фактический результат на основной платформе:
ветка запланированного уведомления недоступна → показывается только немедленное
уведомление, пока приложение активно (подтверждает §5.1).

> **Что не измерено (см. §10):** холодный запуск, потребление памяти, поведение
> напоминаний на реальном устройстве, размер AAB/Play, установленный размер,
> точность доставки alarm при Doze/OEM.

## 7. Требования local-first и резервной копии (влияние на выбор)

Общее для всех нативных вариантов и Expo (все поддерживают):

- **Local-first/offline-first** уже выполняется: данные в SQLite на устройстве, без
  аккаунта и backend.
- **Экспорт в один версионированный файл**: JSON (или SQLite-dump) с полем версии
  схемы экспорта и, желательно, контрольной суммой/хэшем и метаданными (версия
  приложения, дата). Импорт — с миграцией версий и валидацией целостности.
  В Expo: `expo-file-system` + системное «Поделиться»/SAF. В Kotlin: SAF
  (`ACTION_CREATE_DOCUMENT`/`ACTION_OPEN_DOCUMENT`) + `ShareCompat`.
- **Восстановление напоминаний без дублирования**: после импорта — полный
  пересчёт расписания (idempotent-sync уже заложен в Stage 4 §6.7) и отмена
  «сиротских» установленных уведомлений; это соответствует принципу «состояние
  синхронизации не хранится, выводится из данных».
- **Приватность/целостность**: файл не выгружается сам; шифрование — опционально,
  отдельным решением владельца.
- **Периодические напоминания о копии** — необязательная функция, вне текущего
  объёма (владелец разрешил не реализовывать сейчас).

Дополнительная зависимость для Expo: `expo-sharing` / `expo-file-system` (новые
зависимости — требуют утверждения по §8.8 плана Stage 4/Stage 5).

## 8. Рекомендация и план

### 8.1. Основной стек — **оптимизированный Expo / React Native** (контрольный вариант)

Обоснование: сохраняет утверждённые алгоритмы, тесты, дизайн и реализованный Stage 4;
размер приводится к оправданному **без переписывания**; риск и стоимость минимальны.
Ключевая гипотеза, которую нужно **измерить**: shippable-сборка Orbit (release AAB,
per-ABI) укладывается в разумные десятки МБ (ориентир — Play-размер у Expo ≈ 11.7 МБ
на примере SDK 50).

Оптимизации размера (в порядке эффекта):
1. **Release-сборка** вместо debug preview (R8/minify + `shrinkResources`) — даёт
   кратный выигрыш.
2. **AAB / per-ABI (ABI splits)** — вместо universal APK со всеми ABI.
3. Удаление неиспользуемых зависимостей (`@expo/ui`, `expo-glass-effect`,
   `expo-symbols` и пр. — по факту использования), **subsetting шрифтов** (сейчас
   ≈2.9 МБ Unbounded всех начертаний).
4. Отключение ненужных декодеров (`expo-build-properties`: gif/webp), Hermes,
   `useLegacyPackaging` при необходимости.

### 8.2. Альтернатива (если владелец решит про размер/надёжность)

**Kotlin + Jetpack Compose** (Kotlin + Views — если нужен абсолютный минимум).
Даёт нативный минимум размера и максимум предсказуемости батареи, но требует
переписывания UI и повторной реализации домена (перенос утверждённых правил).

### 8.3. План (после решения владельца; сейчас НЕ выполняется)

1. **Диагностика FAIL уведомления** на устройстве (release-сборка): разрешение/
   канал → энергосбережение/Doze → поведение alarm → перезагрузка → OEM-ограничения.
   Отдельно от выбора стека.
2. **Измерение shippable-размера** текущего Expo: собрать release AAB/per-ABI,
   получить Play-оценку, разложить вклад (нативные либы/ABI/ресурсы/ассеты) —
   «не подменять измерения оценками».
3. Если размер/функция приемлемы — **остаться на Expo**, добавить Stage 5/далее.
4. Если нет — отдельное разрешение на миграцию на Kotlin (Compose/Views) по
   утверждённому плану, с сохранением алгоритмов, данных и дизайна.
5. Резервное копирование (local-first) — отдельный Stage по решению владельца.

## 10. Ограничения измерения и нерешённые вопросы

**Не измерено в песочнице (нет устройства/подписи/Play-контура):**
- холодный запуск, потребление памяти, установленный размер — ни для Expo, ни для
  Kotlin (нужно устройство);
- реальный release-APK/AAB/Play-размер *Orbit*;
- фактическая доставка локальных напоминаний (Doze/OEM/перезагрузка) — ключ к FAIL;
- размер Kotlin-приложения полного объёма Orbit (прототип — минимальный).

**Нерешённые вопросы для владельца:**
1. Причина отсутствия уведомления (после диагностики) — стек или конфигурация/OEM?
