# OPENDESIGN_PROMPT.md — готовый промпт для OpenDesign

Это **готовый к использованию промпт**. Скопируйте в OpenDesign (на Windows) всё,
что находится в блоке ниже целиком — от начала до конца, без правок. Промпт
самодостаточен: OpenDesign не нужно знать о кодовой базе Orbit.

Перед запуском держите под рукой `docs/design/UI_BRIEF.md` — это расширенный
контекст, если инструмент попросит детали. Возврат результата — по разделу 9 брифа.

---

```text
Ты — продуктовый UI/UX-дизайнер. Спроектируй мобильный интерфейс приложения Orbit.

КОНТЕКСТ ПРИЛОЖЕНИЯ
Orbit — локальное Android-приложение, которое помогает не терять полезные
социальные связи. Пользователь добавляет людей, фиксирует факты общения, а
приложение подсказывает, когда стоит связаться с человеком снова. Данные только
на устройстве: никакой регистрации, backend и облака.

У каждого контакта есть рекомендуемый интервал (в днях) — естественный ритм
общения с этим человеком. Когда с последнего взаимодействия проходит больше, чем
этот интервал, наступает состояние «пора связаться».

Две стратегии связи (пользователь выбирает одну при добавлении человека):
- «Не потерять связь» (maintain): сохранять контакт, не будучи навязчивым; ритм
  спокойный, интервалы могут постепенно расти; стратегия не сокращает интервал
  ради сближения.
- «Сближаться» (grow): постепенно сближаться, но только при взаимности — интервал
  сокращается, только когда инициатива идёт от другого человека и общение прошло
  хорошо.

ЗАДАЧА
Предложи ТРИ визуально различающихся варианта мобильного интерфейса Orbit.

Требования к вариантам:
1. Все три варианта реализуют ОДНИ И ТЕ ЖЕ пользовательские сценарии (ниже).
   Различаться должны визуальный стиль, компоновка, типографика и способы
   организации информации — но НЕ продуктовая логика.
2. Каждый вариант показывает ТРИ основных экрана:
   (1) главный экран — список контактов;
   (2) добавление контакта;
   (3) карточка контакта.
3. Желательно оформить каждый вариант как интерактивный HTML-прототип с
   возможностью переходить между экранами и демонстрировать основные действия
   (пролистать список, открыть карточку, заполнить форму, зафиксировать общение).
4. Ориентация — портретная, мобильный формат (телефон). Управление — пальцем:
   крупные цели нажатия.
5. Все тексты интерфейса — на русском языке.
6. Демонстрационные данные — реалистичные русские имена и правдоподобная история
   общения (несколько контактов, у части — состояние «пора связаться», у одного —
   пустая история).
7. Не придумывай новые возможности ради оформления.

ЭКРАН 1 — ГЛАВНЫЙ (список контактов)
- Список контактов.
- Контакты, которым пора связаться, — СВЕРХУ; остальные — ниже.
- У каждого контакта: имя; рекомендуемый интервал (в днях); понятное обозначение
  «пора связаться» (для верхней группы).
- Переход в карточку контакта по нажатию.
- Возможность добавить контакт.
- Пустое состояние с понятной подсказкой добавить первого человека.

ЭКРАН 2 — ДОБАВЛЕНИЕ КОНТАКТА
- Поле «Имя» (обязательное).
- Необязательная заметка.
- ОБЯЗАТЕЛЬНЫЙ ЯВНЫЙ выбор стратегии: «Не потерять связь» или «Сближаться».
  Без выбранной стратегии сохранение недоступно. Автоматического выбора по
  умолчанию быть не должно.
- Короткое понятное объяснение различий между стратегиями.
- Кнопка сохранения.
- Понятная валидация формы (что не заполнено и что нужно сделать).

ЭКРАН 3 — КАРТОЧКА КОНТАКТА
- Имя, заметка и выбранная стратегия.
- Рекомендуемый интервал.
- Дата следующего рекомендуемого контакта, если она рассчитывается.
- История взаимодействий (только для чтения).
- Действие «Зафиксировать общение»:
  - выбор инициатора: пользователь / другой человек / взаимно;
  - выбор результата: хорошее общение / короткое общение / нет ответа.
- Понятная обратная связь после сохранения (что сохранилось, как изменился ритм).

UX-ТРЕБОВАНИЯ
- Минимум действий для основных сценариев.
- Удобство управления пальцем, хорошая читаемость.
- Понятные состояния загрузки, ошибок и пустого списка.
- Без лишних украшений; без избыточных карточек, теней, скруглений и анимаций.
- Чистый, современный, функциональный интерфейс.

ЧЕГО НЕ ДОЛЖНО БЫТЬ В ПРОТОТИПЕ
- Уведомлений.
- Авторизации / входа.
- Социальной сети (ленты, подписки, публичные профили).
- AI-функций.
- Редактирования или удаления контактов и взаимодействий.
- Переключения языков.
- Рейтингов людей.
- Неутверждённых настроек.
- Дополнительных экранов и продуктовых возможностей.

ОГРАНИЧЕНИЯ БУДУЩЕЙ РЕАЛИЗАЦИИ
Прототип будет реализован на Expo + React Native. Поэтому предлагай стандартные
мобильные паттерны и компоненты, без web-only приёмов и тяжёлых кастомных
анимаций; состояния экранов (данные / пусто / загрузка / ошибка) должны быть
конкретными и реализуемыми.

РЕЗУЛЬТАТ
- Три визуально различающихся варианта, каждый — с тремя экранами.
- Для каждого варианта кратко опиши визуальное направление, типографику, цвета и
  принципы отступов.
- Не создавай production-код Orbit и не объявляй ни один вариант окончательно
  утверждённым: варианты предлагаются владельцу для выбора.
```

---

## После запуска

1. Просмотри три варианта и выбери (или соедини) направление.
2. Сохрани материалы по списку из `docs/design/UI_BRIEF.md`, раздел 9:
   макеты экранов, прототипы/экспорт, описание визуального направления,
   типографику, цвета, отступы, компоненты и их состояния, особенности навигации.
3. Утверди выбранный дизайн — после этого отдельным шагом готовится `DESIGN.md`.
