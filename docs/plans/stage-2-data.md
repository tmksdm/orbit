# План Stage 2 — Data Layer (порты репозиториев и Expo SQLite)

- Статус: **Draft (ожидает утверждения владельцем)**
- Дата постановки: 2026-10-08

## Goal

Реализовать слой данных local-first: объявить в domain порты репозиториев и
реализовать их на Expo SQLite в `src/data` — хранение контактов и отдельной
истории взаимодействий, версионированные миграции схемы и интеграционные тесты.
Продуктовую логику (scheduling) не трогаем: правила Stage 1 остаются как есть.

## Scope

- Порты репозиториев, объявленные в `src/domain` (интерфейсы, чистый TypeScript,
  без React / Expo / SQLite / UI) — реализуют принцип ARCHITECTURE.md, правило 4.
- Схема SQLite: таблицы `contacts`, `interactions` (+ версия схемы).
- Реализация репозиториев в `src/data` на `expo-sqlite`.
- Раннер миграций (forward-only, версия схемы через `PRAGMA user_version`).
- Интеграционные тесты репозиториев и миграций.
- Обновление документации (`ARCHITECTURE.md`, `docs/TESTING.md`, `docs/DOMAIN.md`
  при необходимости) и `docs/PROJECT_STATE.md`.

## Out of scope

UI и экраны, `features`, уведомления/напоминания, сидирование дефолтов, cloud sync,
authentication, backend, AI. Изменение scheduling-правил и утверждённых множителей.
Реализация следующего Stage (features/UI) — не начинается.

## Technical approach

- Направление зависимостей: `data → domain`. Порты объявляет domain, `src/data`
  даёт реализацию (ARCHITECTURE.md, правила 1 и 4).
- Зависимость: `expo-sqlite` ставится через `npx expo install expo-sqlite`
  (совместимая с Expo SDK 57 версия — не хардкодить номер, сверяться с SDK).
- Таблица `contacts`: `id` (PK), `name`, `note` (NULL допустим), `strategy`,
  `minIntervalDays`, `recommendedIntervalDays`. `note?` из модели Stage 1
  хранится как nullable-столбец.
- Таблица `interactions`: собственный PK, `contactId` (FK → `contacts.id`),
  `initiator`, `outcome`, `occurredAt`. История — отдельная коллекция, не поле
  Contact (модель, согласованная на Stage 1).
- `recordInteraction` остаётся чистой domain-функцией Stage 1; слой данных только
  сохраняет события и обновлённый Contact — расчёт интервала в domain не дублируется.
- API репозиториев асинхронный (Promise) — SQLite-драйвер асинхронный; форма и
  сигнатуры — см. «Решения к утверждению».

## Acceptance criteria

- [ ] Порты репозиториев объявлены в `src/domain` и не импортируют React / Expo /
      react-native / SQLite / UI.
- [ ] Реализация репозиториев на SQLite в `src/data`; direction зависимостей
      `data → domain` соблюдено.
- [ ] CRUD: создание и чтение контакта (все поля; `note` пуст и задан), обновление
      `recommendedIntervalDays`; добавление взаимодействия и чтение истории по контакту.
- [ ] Миграции применяются при старте и идемпотентны (повторный запуск не ломает схему).
- [ ] `npm run lint`, `npm run typecheck`, `npm test` — зелёные.
- [ ] документация обновлена, `docs/PROJECT_STATE.md` дополнен проверенными фактами.
- [ ] Следующий Stage не начат.

## Required tests

- Пустая БД → список контактов пуст.
- Создание + чтение контакта: все поля, `note` отсутствует и `note` задан.
- Обновление `recommendedIntervalDays` сохраняется и читается обратно.
- Добавление взаимодействия + чтение истории по контакту (порядок по времени).
- Взаимодействия изолированы по `contactId` (история одного не попадает в другой).
- Миграция «с нуля» и повторный запуск миграций (идемпотентность, версия схемы).
- Smoke-уровень: инициализация модуля/репозитория не бросает ошибку.

## Manual verification

- Прогон на эмуляторе/устройстве: инициализация БД при старте, добавление данных,
  повторный запуск — данные сохраняются между сессиями.
- Если запуск на устройстве в среде агента недоступен — проверка ограничивается
  интеграционными тестами, и это честно фиксируется в `REVIEW_REPORT.md`.

## Risks

- `expo-sqlite` — нативный модуль; в `jest` (jest-expo) может требовать мока или
  тест-адаптера. Подход выбирает решение 4; ложная зелёнка недопустима.
- Синхронный vs асинхронный доступ: выбран async (Promise) — влияет на сигнатуры портов.
- Миграции forward-only, откатов нет (осознанно для local-first MVP).
- Стартовый интервал нового контакта (7 дней) — открытое решение владельца;
  в Stage 2 дефолты не сидируются и вопрос не закрывается.

## Решения к утверждению до начала реализации

1. **Stage 2 = слой данных.** Подтвердить, что Stage 2 — именно порты + Expo SQLite +
   миграции. Уточнить нумерацию: в `REVIEW_REPORT.md` слой данных упоминался как
   «Stage 3+», а `docs/PROJECT_STATE.md` держит вопрос «отдельный Stage 2 или часть
   следующего этапа».
2. **Форма портов.** Отдельные `ContactRepository` и `InteractionRepository` — или
   единый `OrbitRepository`. И место объявления в domain (предлагается
   `src/domain/ports.ts`).
3. **Асинхронный API.** Порты возвращают `Promise` (предлагается) или синхронный
   интерфейс поверх драйвера.
4. **Подход к тестам данных.** Репозитории тестируются против тест-адаптера/
   in-memory fake без нативного модуля — или подключаем node-совместимую SQLite
   (доп. зависимость). Влияет на состав `devDependencies`.
5. **Новая зависимость.** Добавить `expo-sqlite` (единственная новая зависимость
   Stage 2) — подтвердить.
6. **Миграции.** Ручной раннер на `PRAGMA user_version`, forward-only — ок?
7. **Стартовый интервал 7 дней** остаётся открытым решением владельца и в Stage 2
   не закрывается; сидирование дефолтов в scope не входит — подтвердить.

До утверждения этих пунктов реализация Stage 2 не начинается.
