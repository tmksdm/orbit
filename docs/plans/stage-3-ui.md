## Утверждённые решения владельца (приняты 2026-10-08)

Помечены как принятые; в открытых вопросах не повторяются.

1. **Правило «пора связаться» (due) — принято.** Используется дата последнего
   зафиксированного взаимодействия; если взаимодействий не было — дата создания
   контакта. Формула: `nextDueDate = referenceDate + recommendedIntervalDays`.
   Контакт требует внимания, если рассчитанная дата наступила или прошла. Отдельное
   поле `nextContactAt` НЕ вводится. Нужно поле `createdAt` и forward-only миграция
   SQLite до версии 2. Расчёт due — чистая domain-функция, не в UI.
   **Обработка старых контактов — вариант A (утверждён владельцем, окончательно):**
   для существующих контактов `createdAt` остаётся `NULL` (реальная дата создания
   неизвестна и не восстанавливается); при наличии истории due считается от последнего
   взаимодействия; при отсутствии истории и `createdAt = NULL` срок не рассчитывается
   (контакт виден в списке, интервал показывает, в группу «пора» не попадает). После
   первого взаимодействия опорой становится его `occurredAt`.
2. **Порядок отображения — принято.** Сначала контакты, которым уже пора написать;
   остальные — после них. Внутри групп простой предсказуемый порядок (см. ниже),
   без приоритетов и сложной сортировки.
3. **Выбор стратегии — принято.** При добавлении контакта пользователь обязан
   явно выбрать `maintain` или `grow`; автоматический выбор запрещён. Обе стратегии
   объясняются понятными русскими словами.
4. **Дата взаимодействия — принято.** При фиксации автоматически пишется текущий
   момент (ISO 8601); способ получения времени тестируемый. Выбор произвольной даты
   (в т.ч. задним числом) на Stage 3 НЕ реализуется.
5. **Редактирование и удаление — принято.** В Stage 3 не входят: без экранов,
   кнопок, меню и доп. бизнес-логики.
6. **Язык интерфейса — принято.** UI — русский (названия, подсказки, ошибки,
   обозначения стратегий). Идентификаторы в коде / типах / файлах / полях БД —
   английские. Система локализации и переключения языков на Stage 3 не вводится.

## Goal

Получить минимальное, но реально работающее приложение Orbit на Android: пользователь
добавляет человека, фиксирует факт общения и видит, с кем пора связаться. Список
показывает контакты, у которых наступил срок, и рекомендованный интервал; фиксация
взаимодействия пересчитывает интервал существующей доменной логикой Stage 1. Данные
хранятся локально (SQLite, Stage 2) и переживают перезапуск. Попутно впервые
проверяется работа нативного `expo-sqlite` на устройстве.

Stage 3 — первый вертикальный срез: UI → features → domain/data → SQLite. Продуктовые
правила и алгоритмы Stage 1 не меняются.

## Scope

- **Экраны** (`src/app`, expo-router), минимальный набор:
  1. **Список контактов (главный):** контакты, у которых срок наступил — сверху;
     остальные — ниже; у каждого видно рекомендованный интервал и признак «пора
     связаться»; переход в карточку; корректное пустое состояние.
  2. **Добавление контакта:** имя (обязательно), необязательная заметка, **явный**
     выбор стратегии `maintain`/`grow` (без значения по умолчанию); старт = 2 дня;
     сохранение в SQLite; дата создания фиксируется.
  3. **Карточка контакта:** данные контакта, история взаимодействий (read-only),
     фиксация взаимодействия (инициатор, результат), отображение обновлённого интервала.
- **Слой `src/features`:** use-cases, связывающие UI с domain и data (загрузка списка,
  добавление контакта, фиксация взаимодействия, вычисление due).
- **Слой `src/ui`:** переиспользуемые презентационные компоненты без бизнес-правил.
- **Слой `src/services`:** генерация `id` контакта и источник текущего времени
  (изоляция platform API, тестируемость).
- **Domain:** новая **чистая** функция расчёта due (и сопутствующий тип) в `src/domain`.
- **Data:** forward-only миграция схемы **v2** — добавление `createdAt` у `contacts`
  (только проектирование на текущем шаге; код миграции — на этапе реализации).
- **UI/UX-фаза** с OpenDesign (инструмент дизайна, не runtime-зависимость) и фиксация
  `DESIGN.md` — по фазам ниже, после отдельного разрешения владельца.
- **Тесты:** unit (due-логика), компонентные (RNTL) для критичных потоков; интеграционные
  Stage 2 не ослабляются.
- **Документация:** `docs/PROJECT_STATE.md`, `README.md`, `docs/DOMAIN.md` (раздел due),
  при необходимости `ARCHITECTURE.md` / `docs/TESTING.md`.

## User flows

**F1 — Просмотр списка.**
Открытие → загрузка контактов из SQLite → список. Сверху — контакты, которым пора
(наступила/прошла `nextDueDate`); ниже — остальные. У контакта: имя, рекомендованный
интервал, признак «пора связаться» (для due-группы). Порядок — по правилу из раздела
«Порядок отображения». Пустое состояние — подсказка добавить первого человека. Ошибка
загрузки — понятное сообщение, без падения.

**F2 — Добавление контакта.**
Кнопка «Добавить» → форма: имя (обязательно), заметка (опционально), **обязательный**
выбор стратегии `maintain`/`grow` (см. решение 3). Без выбора стратегии сохранение
недоступно (кнопка неактивна / понятная ошибка). Сохранение → контакт появляется в
списке. `recommendedIntervalDays` = 2 (утверждено), `minIntervalDays` = 2 по умолчанию,
`createdAt` = текущий момент.

**F3 — Фиксация взаимодействия.**
Карточка контакта → «Зафиксировать взаимодействие» → выбор инициатора
(`me`/`them`/`mutual`) и результата (`good`/`short`/`no_reply`) → сохранение через
атомарную операцию Stage 2 (`recorder.record`) с `occurredAt` = сейчас (ISO 8601) →
пересчёт `recommendedIntervalDays` доменной логикой → обновлённый интервал виден в
карточке и списке; событие появляется в истории.

**F4 — Сохранность данных.**
Контакты и взаимодействия сохраняются локально; после полного перезапуска данные
доступны; запись Interaction + Contact атомарна (гарантия Stage 2).

**F5 — Работа на Android.**
Приложение запускается на телефоне; F1–F4 доступны; нативный `expo-sqlite` работает
(открытие БД, миграции v1→v2, запись/чтение, переживание перезапуска).

## Модель данных и миграция v2 (проектирование)

Фактическая схема Stage 2 (миграция v1): `contacts(id, name, note, strategy,
minIntervalDays, recommendedIntervalDays)`, `interactions(id, contactId, initiator,
outcome, occurredAt)`, индекс `idx_interactions_contact(contactId, occurredAt)`,
`PRAGMA user_version`. Поля `createdAt` в v1 нет.

**Миграция v2 (forward-only, `PRAGMA user_version = 2`):**

- Добавить `contacts.createdAt TEXT` (ISO 8601), **допускающее `NULL`** — для
  совместимости с существующими записями (в SQLite `ALTER TABLE ADD COLUMN NOT NULL`
  требует постоянного default). Значения существующих строк миграция НЕ заполняет.
- **Существующие контакты: `createdAt` остаётся `NULL`** — независимо от наличия
  истории. Реальная дата создания неизвестна, и она НЕ восстанавливается ни через
  `MIN(occurredAt)`, ни через момент миграции, ни какой-либо другой предполагаемой
  датой. Дата самого раннего взаимодействия — это не дата создания контакта
  (исправление замечания ревью).
- **Новые контакты (Stage 3+):** приложение обязательно записывает фактическое время
  создания в `createdAt` (ISO 8601).
- Отсутствие `createdAt` у старого контакта **не мешает** расчёту due, если у контакта
  есть история взаимодействий (опора — последнее взаимодействие).
- На практике таблица `contacts` на момент Stage 2 пуста (UI, создающего контакты, ещё
  не существует), поэтому для существующих записей миграция ничего не заполняет.

Расширение доменного типа `Contact` полем `createdAt` выполняется на этапе реализации
(миграция кода + обновление `docs/DOMAIN.md`/`types.ts` отдельным коммитом, без изменения
алгоритмов Stage 1). На текущем шаге код НЕ меняется.

## Due-логика (domain)

Чистая, детерминированная функция (например, `src/domain/due.ts`), без React/Expo/SQLite:
UI и features только отображают её результат.

- **referenceDate** = дата **последнего** взаимодействия (`MAX(occurredAt)` как
  смысловое правило), если история есть; при отсутствии истории — `createdAt`.
- **nextDueDate** = `referenceDate + recommendedIntervalDays` (в календарных днях).
- Контакт **требует внимания**, если `today >= nextDueDate`.
- **Локальная календарная дата.** Сравнение выполняется на уровне календарных дат в
  локальной зоне пользователя, а не моментов времени: и `referenceDate`, и «сегодня»
  приводятся к локальной дате (`YYYY-MM-DD`), затем due = локальная дата reference +
  N дней. Это устраняет влияние времени суток и переходов часовых поясов/DST на границе
  суток: взаимодействие в 23:59 и в 00:01 не «перепрыгивает» день из-за часа.
- **Отсутствие истории:** reference = `createdAt`. Если истории нет и `createdAt`
  отсутствует (старые до-v2 записи) — срок **не рассчитывается**: контакт виден в
  общем списке, рекомендованный интервал отображается, но в группу «пора связаться»
  контакт не попадает (утверждено владельцем, вариант A). После первого взаимодействия
  опорой становится его `occurredAt`.
- Алгоритм пересчёта `recommendedIntervalDays` НЕ изменяется; due только читает текущее
  значение.

## Порядок отображения контактов

- **Группа 1 — «пора»:** контакты с `today >= nextDueDate`.
- **Группа 2 — «остальные»:** все прочие (включая контакты без рассчитываемого срока).
- Внутри каждой группы: по возрастанию `nextDueDate` (у группы 1 — самые «просроченные»
  сверху; у группы 2 — ближайшие сверху; для контактов без срока — в конце группы),
  при совпадении — по имени (`COLLATE NOCASE`), затем по `id` (устойчивый детерминант).
- Никаких рейтингов, приоритетов и дополнительных категорий не вводится.

## Technical approach

- Слои и направление зависимостей — `ARCHITECTURE.md`:
  `app → features → { ui, services, data } → domain`. Domain — чистый TS.
- Экраны (`src/app`) отображают состояние и вызывают use-cases из `src/features`;
  бизнес-логику и SQL не содержат.
- Доступ к данным — только через фасад Stage 2: `openOrbitDatabase()` →
  `{ db, contacts, interactions, recorder }`; `contacts.list/getById/save`,
  `interactions.listByContact`, `recorder.record(contactId, interaction)` (атомарно).
- Пересчёт интервала — существующие доменные функции `createContact` (старт = 2 дня) и
  `recordInteraction` (множители Stage 1); в features/UI не дублируются.
- **Генерация `id` (предложение, стандартное):** `expo-crypto` → `Crypto.randomUUID()`
  (официальный модуль Expo, совместим с SDK 57). Зависимость добавляется на этапе
  реализации (`npx expo install expo-crypto`), обоснование — надёжный UUID без своего
  кода. Альтернатива без зависимости (UUID на `Math.random`) слабее и отклонена.
- **Время (предложение, тестируемость):** тонкий источник времени в `src/services`
  (например, `now(): string` → `new Date().toISOString()`), внедряемый в features и
  подменяемый в тестах фиксированным значением. Домен остаётся детерминированным:
  due-функция принимает «сегодня» параметром, а не читает часы сама.
- **Хранение времени:** ISO 8601 (UTC, `toISOString()`); для сравнения due приводится к
  локальной календарной дате (см. «Due-логика»).
- **Организация UI-компонентов (предложение):** один компонент на состояние экрана
  (пусто/загрузка/ошибка/данные) в `src/ui`; экраны композируют их и вызывают
  use-cases. Без лишних абстракций.
- **Состояния экранов** (пусто/загрузка/ошибка/данные) обрабатываются во features и
  отображаются в `src/ui`.
- **Тестируемость:** due-логика — unit-тесты с фиксированными датами; компонентные
  тесты RNTL с подставными реализациями портов Stage 2 и подставным временем.

## UI/UX workflow (OpenDesign)

OpenDesign (https://github.com/nexu-io/open-design) — **инструмент дизайна и
прототипирования**, НЕ runtime-зависимость Orbit. Он создаёт single-page HTML-прототипы,
читающие `DESIGN.md`; прототипы НЕ переносятся в React Native напрямую.

Принятый порядок работы:

1. Согласование этого плана Stage 3.
2. Подготовка дизайн-брифа на основе утверждённых сценариев.
3. Создание вариантов мобильного интерфейса через OpenDesign.
4. Просмотр и выбор варианта владельцем.
5. Утверждение дизайна.
6. Фиксация дизайн-системы в `DESIGN.md`.
7. Реализация интерфейса в Expo + React Native.
8. Проверка на Android.

Ориентиры (не утверждённая дизайн-система): минимализм, простота, читаемость, удобные
элементы управления на телефоне, минимум визуального шума, без декоративных элементов
и избытка карточек/скруглений/теней/анимаций.

Среда: OpenDesign — agent-native workspace (Apache-2.0), работает поверх уже
установленного coding agent (skills/CLI/MCP); desktop-сборки — macOS и Windows; для
Linux prebuilt-артефакта нет (исходники/Docker). Песочница агента — Linux, GUI OpenDesign
там не поднимается. Практический путь: владелец запускает OpenDesign на Windows (или,
по его решению, дизайн согласуется иначе). Это операционный момент, а не продуктовая функция.

**На текущем шаге:** OpenDesign НЕ устанавливается, прототипы НЕ генерируются, код
интерфейса НЕ пишется. Дизайн согласуется с владельцем до реализации.

## Required tests

- **Unit (domain, due):**
  - контакт с историей — reference = **последнее** взаимодействие (при нескольких
    взаимодействиях берётся последнее по `occurredAt`, а не первое);
  - без истории — reference = `createdAt`;
  - без истории и без `createdAt` — срок не рассчитывается;
  - границы «due / не due» (ровно `nextDueDate`, на день раньше, на день позже);
  - смена дня/часового пояса не сдвигает вердикт из-за времени суток.
- **Unit (domain, интервал):** значение НЕ опускается ниже `minIntervalDays`
  (например, `grow` при интервале = 2 и `them + good` остаётся 2). Существующие 30
  domain-тестов Stage 1 не ослабляются.
- **Компонентные (RNTL):**
  - список: пусто / с данными; due-контакты выше остальных; порядок внутри групп;
  - форма добавления: **сохранение недоступно без выбранной стратегии** (проверка
    решения 3); имя обязательно; старт = 2 дня;
  - карточка: фиксация взаимодействия, отображение нового интервала.
- **Интеграционные (Stage 2, миграции и due):**
  - существующий контакт **с историей**: после миграции `createdAt = NULL`, due
    считается от последнего взаимодействия;
  - существующий контакт **без истории**: `createdAt = NULL`, срок не рассчитывается;
  - **новый** контакт без истории: `createdAt` заполнен, срок считается от даты создания;
  - контакт с несколькими взаимодействиями: опора — последнее по `occurredAt`;
  - повторный запуск миграции не изменяет данные и не ломает схему (идемпотентность).
  - Существующие 20 интеграционных тестов Stage 2 не ослабляются.
- **Smoke:** приложение стартует, главный экран рендерится.

## Manual verification (Android)

**Обязательно для окончательной приёмки Stage 3.** Проверка нативного `expo-sqlite`
на Android не может быть заменена тестами `node:sqlite`.

Если агент не может сам проверить приложение на Android, он обязан:

1. подготовить воспроизводимую инструкцию владельцу (сборка/запуск, что именно смотреть);
2. предоставить чек-лист ручного тестирования (ниже);
3. дождаться результата проверки;
4. зафиксировать **реальные** результаты в `REVIEW_REPORT.md`.

Отсутствие Android-окружения у агента НЕ является основанием объявить проверку
выполненной или Stage завершённым.

Чек-лист владельцу:

1. Установить/запустить приложение на Android (эмулятор или устройство).
2. Пустой список → добавить контакт (стратегия выбрана явно) → контакт в списке,
   интервал = 2.
3. **Проверка роста:** зафиксировать `no_reply` → интервал 2 → 4; повторить → 8.
4. **Проверка сокращения (REVIEW-01, корректный сценарий):** на контакте со стратегией
   `grow` и интервалом **выше минимума**, полученным допустимой последовательностью
   (например, `no_reply` дал 4), зафиксировать `them + good` → интервал 4 → 3
   (×0.8, выше `min = 2`). Так проверяется именно сокращение, а не упор в минимум.
5. **Проверка нижней границы:** на контакте с интервалом = 2 зафиксировать
   `them + good` → интервал остаётся 2 (ниже минимума не опускается).
6. Полностью закрыть и перезапустить приложение → контакты, интервалы и история на месте.
7. Проверить главный экран: контакты с наступившим сроком — сверху.
8. Оценить удобство основных сценариев на телефоне.

## Risks

- **Проверка Android недоступна агенту** (нет Android-окружения). Митигация: явный
  обязательный чек-лист и инструкция владельцу; Stage 3 не принимается без фактической
  проверки (REVIEW-02). До проверки поведение нативного `expo-sqlite` считается
  непроверенным (Stage 2 подтвердил только `node:sqlite`).
- **Границы суток и часовые пояса** в due-расчёте. Митигация: сравнение по локальной
  календарной дате (не по моменту времени) + unit-тесты границ.
- **`createdAt` старых записей.** Митигация (утверждено, вариант A): значение остаётся
  `NULL`, выдуманные даты не подставляются (`MIN(occurredAt)` НЕ используется как дата
  создания); при истории due считается от последнего взаимодействия, без истории —
  срок не рассчитывается. Риск искажения данных устранён.
- **OpenDesign не запускается в песочнице агента (Linux).** Митигация: владелец
  запускает на Windows, либо дизайн согласуется иным способом по его решению.
- **Расползание UI-объёма.** Митигация: явный scope, минимальный набор экранов,
  запрет новых продуктовых функций.
- **Утечка domain-логики в компоненты.** Митигация: расчёты только в domain, ревью, тесты.
- **Новая зависимость `expo-crypto`.** Митигация: официальный модуль Expo, обоснован
  (надёжный UUID), добавляется на этапе реализации, а не сейчас.

## Open questions

**Блокирующих продуктовых вопросов нет.** Все необходимые решения приняты владельцем
(разделы «Утверждённые решения владельца» и миграция `createdAt` — вариант A) и здесь
не повторяются. Технические решения с очевидными стандартными реализациями (генерация
UUID, организация UI-компонентов, тестируемое внедрение времени, использование
существующих зависимостей) предложены в «Technical approach» с кратким обоснованием.

План ожидает финального ревью и approval владельца; при его утверждении открытых
вопросов не остаётся.

## Stage boundary (что означает завершение Stage 3)

- Пользователь на Android: добавляет контакты, фиксирует взаимодействия, видит
  пересчитанный интервал и контакты, которым пора (due сверху); данные сохраняются
  между запусками.
- Нативный `expo-sqlite` **проверен на устройстве** (обязательно); результаты зафиксированы
  в `REVIEW_REPORT.md`. Без этого Stage 3 не принимается.
- Domain остаётся чистым; правила и алгоритмы Stage 1 не изменены.
- Выполнен ритуал завершения Stage (`AGENTS.md`): проверки зелёные, обновлён
  `REVIEW_REPORT.md`, изменения подготовлены к внешнему ревью; следующий Stage
  самостоятельно не начинается.
