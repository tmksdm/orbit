# План Stage 3 — первый UI на Android

- Статус: **DRAFT — ожидает утверждения владельца**
- Дата постановки: 2026-10-08

Реализация Stage 3 НЕ начинается до утверждения этого плана и открытых вопросов
(разделы «Открытые вопросы» и «UI/UX workflow»). Документ — источник объёма работ
Stage 3; он не заменяет `docs/PRODUCT.md` и `docs/DOMAIN.md`.

## Goal

Получить минимальное, но реально работающее приложение Orbit на Android, в котором
пользователь может: добавить человека, зафиксировать факт общения и увидеть, с кем
пора связаться. Экран «с кем связаться» должен показывать рекомендованный интервал;
фиксация взаимодействия пересчитывает интервал существующей доменной логикой Stage 1.
Данные хранятся локально (SQLite, Stage 2) и переживают перезапуск приложения.
Попутно — впервые проверить работу нативного `expo-sqlite` на устройстве.

Stage 3 — первый вертикальный срез: UI → features → domain/data → SQLite.
Продуктовые правила и алгоритмы Stage 1 не меняются.

## Scope

- Экраны (минимальный набор, `src/app`, expo-router):
  1. **Список контактов** (главный): все контакты; понятная индикация «с кем пора
     связаться»; показ рекомендованного интервала; переход в карточку контакта;
     корректное пустое состояние.
  2. **Добавление контакта:** имя, необязательная заметка, выбор стратегии
     `maintain` / `grow`; стартовый интервал = утверждённые 2 дня; сохранение в SQLite.
  3. **Карточка контакта:** данные контакта, история взаимодействий (read-only),
     фиксация взаимодействия (инициатор, результат), показ обновлённого интервала.
- Слой `src/features`: use-cases, связывающие UI с domain и data (загрузка списка,
  добавление контакта, фиксация взаимодействия).
- Слой `src/ui`: переиспользуемые презентационные компоненты без бизнес-правил.
- Возможный `src/services`: генерация идентификатора контакта и работа с датой/временем
  (изоляция platform API). Конкретное решение — в «Открытых вопросах».
- Возможная доменная функция «пора ли связаться» (due-логика) как **чистая** функция
  в `src/domain` — только если владелец утвердит её правила (см. «Открытые вопросы»);
  в UI вычисления не переносятся.
- UI/UX-фаза с OpenDesign (как инструмент дизайна и прототипирования) и фиксация
  `DESIGN.md` — по фазам ниже, после отдельного разрешения владельца.
- Тесты: компонентные (RNTL) для критичных потоков, unit-тесты для новой чистой
  логики (due-логика, если утверждена), интеграционные — уже есть на Stage 2.
- Обновление документации: `docs/PROJECT_STATE.md`, `README.md`, при необходимости
  `ARCHITECTURE.md` / `docs/TESTING.md` / `docs/DOMAIN.md` (при добавлении due-логики).

## Out of scope

- Уведомления/напоминания (если отдельно не утверждены в scope Stage 3 — по
  ограничению задачи они не реализуются).
- Backend, авторизация, облачная синхронизация, AI.
- Изменение утверждённых алгоритмов интервалов и правил Stage 1.
- Редактирование/удаление контактов и взаимодействий (в MVP не требуется; см. «Открытые вопросы»).
- iOS-специфичная работа (первая платформа — Android).
- Новые архитектурные абстракции «на будущее», новые самостоятельные Stage.
- Перенос HTML/CSS-прототипа OpenDesign в приложение как кода; замена стека
  веб-приложением. OpenDesign — только инструмент дизайна.

## User flows

**F1 — Просмотр списка.**
Открытие приложения → загрузка контактов из SQLite → список. У контакта видно:
имя, рекомендованный интервал и признак «пора связаться» (для контактов, у которых
срок наступил). Пустое состояние — подсказка добавить первого человека. Ошибка
загрузки — понятное сообщение (без падения).

**F2 — Добавление контакта.**
Кнопка «Добавить» → форма (имя обязательно; заметка — опционально; стратегия
`maintain`/`grow`, по умолчанию `maintain`) → сохранение → новый контакт появляется
в списке. `recommendedIntervalDays` = 2 (утверждено), `minIntervalDays` = 2 по умолчанию.

**F3 — Фиксация взаимодействия.**
Карточка контакта → «Зафиксировать взаимодействие» → выбор инициатора
(`me`/`them`/`mutual`) и результата (`good`/`short`/`no_reply`) → сохранение через
атомарную операцию Stage 2 (`recorder.record`) → пересчёт `recommendedIntervalDays`
доменной логикой → обновлённый интервал виден в карточке и списке; событие появляется
в истории контакта.

**F4 — Сохранность данных.**
Контакты и взаимодействия сохраняются локально; после полного перезапуска приложения
данные доступны; запись Interaction + Contact атомарна (гарантия Stage 2).

**F5 — Работа на Android.**
Приложение запускается на телефоне; F1–F4 доступны; нативный `expo-sqlite` работает
(открытие БД, миграции, запись/чтение, переживание перезапуска).

## UI/UX workflow (OpenDesign)

OpenDesign (https://github.com/nexu-io/open-design) используется **только как
инструмент дизайна и прототипирования** — НЕ как runtime-зависимость Orbit. Он
создаёт single-page HTML-прототипы, читающие `DESIGN.md`; эти прототипы НЕ переносятся
в React Native напрямую (см. «Технический подход», фаза 4).

Замечания по среде (исследовано в документации проекта):
- OpenDesign — agent-native workspace (Apache-2.0), работает поверх уже установленного
  coding agent (skills / CLI / MCP: `od mcp install <agent>`); desktop-приложения —
  macOS и Windows; для Linux prebuilt-артефакта нет (запуск из исходников или Docker).
- Владелец работает на Windows — desktop-версия OpenDesign доступна ему напрямую.
  В песочнице агента (Linux) полноценный GUI OpenDesign запускать не предполагается.
- Прототипы — HTML-артефакты; они нужны для согласования дизайна, а не для запуска в приложении.

### Фаза 1 — требования к интерфейсу (без OpenDesign)

Результат: короткий документ требований (в рамках этого плана / отдельным файлом) —
минимальный набор экранов и переходы, основные действия, состояния экранов
(пусто / есть данные / загрузка / ошибка), требования к удобству на Android.

Критерий проверки: требования покрывают F1–F4 и не добавляют функций вне scope.

### Фаза 2 — прототипирование в OpenDesign (после отдельного разрешения владельца)

Шаги: дизайн-бриф на основе утверждённых сценариев → варианты мобильного интерфейса
средствами OpenDesign → владелец смотрит и сравнивает → обратная связь → доработка
выбранного варианта → явное утверждение дизайна.

Ориентиры (не утверждённая дизайн-система): минимализм, простота, читаемость,
удобные элементы управления на телефоне, минимум визуального шума, без декоративных
элементов и без избытка карточек/скруглений/теней/анимаций.

Критерий проверки: владелец выбрал и явно утвердил один вариант прототипа.

### Фаза 3 — фиксация дизайн-системы (`DESIGN.md`)

Результат: `DESIGN.md` — типографика, цвета, отступы, размеры интерактивных
элементов, компоненты и их состояния, навигация, правила адаптации под мобильные
экраны; документ соответствует реальным возможностям React Native и не дублирует
продуктовую документацию.

Критерий проверки: по `DESIGN.md` можно реализовать экраны без дополнительных
дизайн-решений; документ согласован владельцем.

### Фаза 4 — реализация в Expo + React Native (только после согласования)

Перенос утверждённых решений в RN-компоненты; подключение существующих domain/data
слоёв; нативные компоненты и совместимые библиотеки; **никакого прямого переноса
HTML/CSS-прототипа**; добавление тестов (см. «Required tests»).

Критерий проверки: экраны реализованы, проверки (lint/typecheck/test) зелёные,
сценарии F1–F4 работают на эмуляторе/устройстве.

### Фаза 5 — проверка на Android

Запуск приложения; проверка SQLite на устройстве; сохранение данных после
перезапуска; фиксация взаимодействий и пересчёт интервалов; удобство основных
сценариев; исправление найденных проблем в рамках Stage 3.

Критерий проверки: пройден чек-лист «Manual verification». Если ручная проверка
в среде агента невозможна — подготавливается инструкция владельцу, и это честно
фиксируется (проверка НЕ объявляется выполненной, если не проводилась).

## Technical approach

- Слои и направление зависимостей — по `ARCHITECTURE.md`:
  `app → features → { ui, services, data } → domain`. Domain остаётся чистым TS.
- Экраны — `src/app` (expo-router): список, форма добавления, карточка контакта.
  Экраны отображают состояние и вызывают use-cases из `src/features`, бизнес-логику
  не содержат.
- Доступ к данным — только через существующие порты/фасады Stage 2:
  `openOrbitDatabase()` → `{ db, contacts, interactions, recorder }`;
  `contacts.list/getById/save`, `interactions.listByContact`,
  `recorder.record(contactId, interaction)` (атомарно). Своих SQL в UI нет.
- Пересчёт интервала — существующие доменные функции: `createContact` (старт = 2 дня)
  и `recordInteraction` (множители Stage 1). Не дублируются ни в features, ни в UI.
- Идентификатор контакта и время взаимодействия — способ ещё не утверждён (см.
  «Открытые вопросы»): кандидат — `src/services` (например, `expo-crypto`/`uuid` для id,
  `occurredAt` = текущий момент в ISO 8601). Новые зависимости — только по согласованию.
- Due-логика («пора ли связаться») при утверждении правил реализуется **чистой
  функцией в `src/domain`** и покрывается unit-тестами; UI только отображает результат.
  До утверждения правил экран может показывать рекомендованный интервал как число,
  без вычисления «срока».
- Состояния экранов: пусто / загрузка / ошибка / есть данные — обрабатываются во
  features и отображаются в `src/ui`.
- Тестируемость: доменная логика — unit-тесты; критические потоки UI — компонентные
  тесты RNTL с подставными реализациями портов (интерфейсы Stage 2 позволяют подмену).

## Acceptance criteria

- [ ] Главный экран показывает контакты, рекомендованный интервал и признак «пора
      связаться»; есть корректное пустое состояние; можно открыть контакт.
- [ ] Добавление контакта: имя, необязательная заметка, стратегия `maintain`/`grow`;
      старт = 2 дня; контакт сохраняется в SQLite.
- [ ] Фиксация взаимодействия: инициатор и результат; событие сохраняется; интервал
      пересчитывается существующей доменной логикой и отображается обновлённым.
- [ ] Данные переживают перезапуск приложения; запись Interaction + Contact атомарна.
- [ ] Приложение запускается и работает на Android (проверка нативного `expo-sqlite`).
- [ ] Domain остаётся чистым TS; направление зависимостей соблюдено; алгоритмы Stage 1
      и продуктовые правила не изменены.
- [ ] `npm run lint`, `npm run typecheck`, `npm test` — зелёные.
- [ ] Документация обновлена, `docs/PROJECT_STATE.md` дополнен проверенными фактами.
- [ ] Продуктовые/дизайн-решения, не утверждённые ранее, вынесены владельцу (не
      приняты агентом самостоятельно).

## Required tests

- Unit (domain, если due-логика утверждена): границы «пора / не пора», отсутствие
  истории, влияние `no_reply`/рост интервала — на чистых функциях.
- Компонентные (RNTL): список (пусто / с данными), форма добавления (валидация имени,
  выбор стратегии, сохранение), карточка контакта (фиксация взаимодействия,
  отображение нового интервала).
- Интеграционные (уже есть, Stage 2): репозитории, миграции, атомарность, foreign keys —
  не ослаблять.
- Smoke: приложение стартует, главный экран рендерится.

## Manual verification (Android)

Чек-лист для владельца (или для агента, если среда позволит):

1. Установить/запустить приложение на Android (эмулятор или устройство).
2. Открыть пустой список → добавить контакт → контакт виден в списке, интервал = 2.
3. Зафиксировать взаимодействие (`them` + `good` при стратегии `grow`) → интервал
   уменьшается по правилам домена; событие в истории.
4. Зафиксировать `no_reply` → интервал удваивается; отображение обновляется.
5. Полностью закрыть и перезапустить приложение → контакты и история на месте.
6. Проверить удобство основных сценариев на телефоне.

Если ручная проверка в среде агента недоступна — подготовить понятную инструкцию
владельцу; не утверждать, что проверка выполнена, если она не проводилась.

## Risks

- **Отсутствует опорная дата для «срока».** В текущей модели Contact нет `createdAt`,
  а порт взаимодействий отдаёт историю; для вычисления «пора ли связаться» нужна
  дата отсчёта. Без решения владельца (см. «Открытые вопросы») due-индикатор
  реализовать корректно нельзя — риск неверных вычислений.
- **Нативный `expo-sqlite` не проверялся на устройстве** (Stage 2 подтвердил только
  `node:sqlite`). Проверка включена в фазу 5; до неё поведение на Android считается
  непроверенным.
- **OpenDesign не является runtime-зависимостью и не запускается в песочнице агента
  (Linux).** Реалистичный путь — владелец запускает OpenDesign на Windows; иначе
  фаза 2 может быть выполнена иначе или пропущена по решению владельца.
- **Риск «расползания» UI-объёма.** Митигируется явным scope, минимальным набором
  экранов и запретом новых продуктовых функций.
- **Риск утечки domain-логики в компоненты.** Митигируется правилом «вычисления —
  только в domain», ревью и тестами.
- **ID и время** — без утверждённого решения генерация `id`/`occurredAt` может
  оказаться несогласованной; см. «Открытые вопросы».

## Open questions

Ни одно из решений ниже не принято агентом. Требуется решение владельца.

1. **Правило «пора связаться» (due).** Как вычислять срок и что считать
   просроченным? Варианты:
   - (a) «пора», если от даты последнего взаимодействия прошло ≥
     `recommendedIntervalDays`; при отсутствии взаимодействий — от даты создания
     контакта (**требует добавить `createdAt` в Contact и миграцию схемы v2**);
   - (b) хранить явную дату следующего контакта (`nextContactAt`) и обновлять её
     при фиксации взаимодействия (**новая колонка + миграция v2**, due сравнивается
     с «сегодня»);
   - (c) не вычислять срок на Stage 3 — показывать только число дней интервала.
   Последствия: (a)/(b) дают экран «с кем связаться», но требуют изменения
   схемы/domain (миграция v2, forward-only); (c) — минимальнее, но не выполняет
   сценарий «видно, с кем пора связаться».
2. **Правила отображения просроченных.** Как показывать «пора» (число дней
   просрочки? метка? сортировка списка — сначала due?), группировать ли по времени.
   Последствия: влияет на UX и на порядок списка.
3. **Опорная дата при отсутствии истории.** Для нового контакта без взаимодействий —
   считать срок от даты создания или сразу считать «не пора»? Связано с п. 1.
4. **Генерация `id` контакта.** Где и чем (например, `expo-crypto`
   `randomUUID()` / пакет `uuid`)? Нужна ли новая зависимость. Последствия: выбор
   влияет на зависимости и тестируемость.
5. **Время взаимодействия.** `occurredAt` — «сейчас» при фиксации (ISO 8601, какая
   таймзона)? Нужно ли позволять выбрать дату в прошлом (не входит в F3)?
6. **Редактирование/удаление.** В MVP не требуется; подтвердить, что остаётся вне
   scope Stage 3 (при «нет» — расширение объёма и новые экраны).
7. **Состав экранов.** Достаточно ли трёх экранов (список / добавление / карточка),
   или карточку контакта и форму фиксации взаимодействия нужно разделить.
8. **Язык интерфейса.** Русский или английский (документация продукта — русская;
   кода/идентификаторов — английский).
9. **OpenDesign: кто и как запускает.** Запускает ли владелец OpenDesign на Windows
   сам, или агент готовит брифы/варианты иначе; нужен ли владельцу отдельный
   инструктаж. Последствия: без запуска OpenDesign фаза 2 не выполняется.
10. **Уведомления.** Подтвердить, что напоминания вне Stage 3 (по ограничению задачи).

## Stage boundary (что означает завершение Stage 3)

- Пользователь на Android: добавляет контакты, фиксирует взаимодействия, видит
  пересчитанный интервал и (при утверждённом правиле due) с кем пора связаться;
