# AGENTS.md — операционный контракт для coding agents (проект Orbit)

Orbit — мобильное приложение (Expo + React Native + TypeScript), local-first, без
backend. Этот файл — краткий контракт, как агенту работать в репозитории; он не
должен превращаться в спецификацию продукта. Детали — в документах из карты ниже.

Технические детали Expo/SDK (версии команд, роутинг в `src/app`, Continuous Native
Generation — не создавать `ios/`/`android/` руками, использовать `npx expo install`
для совместимых версий пакетов): см. `AGENTS.md`-подсказки шаблона Expo и
https://docs.expo.dev/versions/ — не полагаться на память, а сверяться с документацией
своей версии SDK.

## Рабочий контракт

1. **Работай только над текущим approved Stage.** Источник истины по текущей
   стадии, её статусу и следующему шагу — `docs/PROJECT_STATE.md`. Краткое
   упоминание стадии в других документах (например, в `README.md`) допустимо, но
   не должно ему противоречить.
2. **Сначала читай быстрый вход:** `AGENTS.md` (этот файл) и `docs/HANDOFF.md`, затем —
   документы по задаче: `docs/PROJECT_STATE.md` (подробный журнал), `ARCHITECTURE.md`,
   `docs/DOMAIN.md`, `docs/DEVELOPMENT.md`, `docs/TESTING.md` и план текущего Stage в
   `docs/plans/`.
3. **Не добавляй незапрошенные функции** — ни продуктовые, ни «попутные»
   инфраструктурные. Объём работ определяет план текущего Stage, не твои идеи.
4. **Не меняй product/domain поведение молча.** Изменение поведения = отдельный
   коммит + обновление соответствующего документа (`docs/PRODUCT.md`,
   `docs/DOMAIN.md`).
5. **Держи domain logic вне React-компонентов:** `src/domain` — чистый TypeScript
   без импортов react, expo, react-native, sqlite и UI. Направление зависимостей —
   `ARCHITECTURE.md`.
6. **Перед завершением задачи запускай и добивайся зелёного статуса:**
   `npm run lint && npm run typecheck && npm test`.
7. **Не ослабляй тесты ради зелёного CI:** не удаляй, не скипай и не смягчай
   проверки. Падение теста — повод чинить код (или явно обсудить сам тест), а не
   подгонять отчёт.
8. **Делай небольшие логические коммиты** в формате Conventional Commits
   (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`).
9. **Перед каждым коммитом проверяй `git diff`** — в коммит попадает только то,
   что задумано.
10. **Не переходи к следующему Stage самостоятельно:** следующий Stage стартует
    только после ревью и явного одобрения результатов текущего.
11. **Работай напрямую в `main`.** Отдельные ветки и Pull Request'ы не используются:
    коммиты и пуш идут в `main` в рамках явно порученной задачи (см. «Workflow»).
12. **Коммит и push в `main` разрешены** в рамках порученной задачи — без отдельной
    просьбы владельца, но только после обязательных проверок и просмотра `git diff`.
13. **Запрещены force push, переписывание опубликованной истории и перезапись чужих
    изменений.**
14. **После законченной логической части остановись** и передай владельцу ссылку на
    коммит для независимого ревью; замечания исправляй **новыми** коммитами.

## Workflow (прямые коммиты в main)

Основной канал — **GitHub**, работа напрямую в `main`; обмен патчами через AI Drive
(`docs/SYNC.md`) — **резервный**. **Ветки, Pull Request'ы и merge не используются.**

1. **Проверки.** Перед коммитом — `npm run lint && npm run typecheck && npm test`
   (зелёные) плюс дополнительные проверки из плана задачи.
2. **Просмотр diff.** Перед коммитом проверить `git diff` — в коммит идёт только задуманное.
3. **Коммит и push в `main`.** Небольшие логические коммиты (Conventional Commits);
   `git commit` и `git push` в `main` выполняются агентом в рамках порученной задачи.
4. **Безопасность.** Запрещены `force push`, переписывание опубликованной истории и
   перезапись чужих изменений.
5. **Передача на ревью.** После законченной логической части — остановиться и передать
   владельцу ссылку на коммит; владелец передаёт её независимому ревьюеру.
6. **Правки.** Замечания ревью исправляются **новыми** коммитами (история не переписывается).
7. **Следующий Stage.** Только после явного разрешения владельца; самостоятельно не начинать.

## Ритуал завершения Stage

После завершения каждого Stage агент обязан:

1. остановить разработку — новые функции и следующий Stage не трогать;
2. выполнить `npm run lint && npm run typecheck && npm test` и добиться зелёного результата
   (плюс дополнительные проверки из плана Stage);
3. создать или обновить `REVIEW_REPORT.md` в корне проекта (структура — по утверждённому шаблону отчёта);
4. закоммитить результат и запушить **напрямую в `main`** (см. «Workflow»);
5. остановиться и передать владельцу ссылку на коммит для независимого ревью;
6. не переходить к следующему Stage самостоятельно — только с явного разрешения владельца.

| Документ | Назначение |

| `docs/PROJECT_STATE.md` | журнал состояния: проверенные факты, следующий шаг — читать первым |

| `docs/PRODUCT.md` | продуктовое видение, принципы, сценарии MVP |
| `docs/DOMAIN.md` | глоссарий domain-концепций и принципы стратегий |
| `docs/HANDOFF.md` | быстрый вход в проект: текущий Stage, статус, задача, ссылки |

| `docs/TESTING.md` | тестовая стратегия |
| `docs/plans/` | планы Stage'ей и шаблон плана |

| `docs/SYNC.md` | протокол обмена файлами с ноутбуком пользователя |

```bash
npm start          # expo start (dev server)
npm run android    # запуск на Android
npm run lint       # eslint
npm run typecheck  # tsc --noEmit
npm test           # jest (jest-expo + @testing-library/react-native)
npm run format     # prettier --write .
```

## Передача файлов между пользователем и агентом

**Основной канал — GitHub.** Изменения коммитятся и пушатся **напрямую в `main`**
(ветки и PR не используются; см. раздел «Workflow» и `docs/DEVELOPMENT.md`). После
законченного этапа агент передаёт владельцу ссылку на коммит для независимого ревью.

**Резервный канал — обмен срезом через AI Drive** (`docs/SYNC.md`); используется, если
GitHub недоступен или владелец отдельно просит патч. Пользователь работает на ноутбуке
(Windows, `D:\Pr\orbit`).

- **Получить код (резерв):** `gsk aidrive download /orbit_sync/from_laptop/orbit_from_laptop.zip <куда>`
  вместе с `PUSH_INFO.txt` (там ветка, коммит и sha256 архива). Сверить sha256 перед распаковкой.
- **Отдать изменения (резерв):** `bash tools/sync/make_patch.sh -d <корень проекта> -v <ГГГГММДД-NN> -m "<что сделано>" <файлы…>`.
  Скрипт собирает архив с описанием и выкладывает его в `/orbit_sync/to_laptop`; пользователь
  забирает патч двойным щелчком по `orbit.cmd`, пункт 3.
- Патч выкладывать только на законченном и проверенном этапе. Правки пользователя не перезаписывать без его просьбы.
- Перед отправкой и приёмом по AI Drive напоминать пользователю включить VPN: без него его сеть
  отклоняет запросы к Genspark.
- В распакованном архиве `git status` может показывать все файлы изменёнными — это переводы строк
  Windows, а не правки. Смотреть реальные изменения: `git diff --ignore-cr-at-eol`.
  Новые файлы создавать с LF (добавить `.gitattributes` с `* text=auto eol=lf`).
- В архив не попадают `.env`, ключи, `node_modules`, базы — состав берётся по правилам `.gitignore`.

## Состояние проекта

В новом чате читать **`AGENTS.md` и `docs/HANDOFF.md`** (быстрый вход), затем — только
документы, относящиеся к порученной задаче. `docs/PROJECT_STATE.md` — подробный журнал
проверенных фактов: обновлять после каждого законченного этапа (только проверенными
фактами) и поддерживать `docs/HANDOFF.md` **актуальным при существенном изменении
состояния проекта** (новый Stage, смена статуса/задачи, закрытие вопросов).

## Экономичный режим работы

1. Контекст читать по карте, а не целиком: сначала `AGENTS.md` и `docs/HANDOFF.md`,
   далее — документы по задаче; `docs/PROJECT_STATE.md` — подробный журнал.
2. Один этап за окно; не начинать следующий, пока текущий не зелёный.
3. Тесты — точечно во время работы, полный прогон перед коммитом/пушем.
4. В коммит — только изменённые файлы. Резервный патч (`make_patch.sh`) — только
   изменённые файлы (явный список путей).
5. Не пересказывать документы в ответах — ссылаться на разделы.
6. Короткие ответы: главное сверху, без повторов.
