# AGENTS.md — операционный контракт для coding agents (проект Orbit)

Orbit — мобильное приложение (Expo + React Native + TypeScript), local-first, без
backend. Этот файл — краткий контракт, как агенту работать в репозитории; он не
должен превращаться в спецификацию продукта. Детали — в документах из карты ниже.

Технические детали Expo/SDK (версии команд, роутинг в `src/app`, Continuous Native
Generation — не создавать `ios/`/`android/` руками, использовать `npx expo install`
для совместимых версий пакетов): см. `AGENTS.md`-подсказки шаблона Expo и
https://docs.expo.dev/versions/ — не полагаться на память, а сверяться с документацией
своей версии SDK.

## Рабочий контракт

1. **Работай только над текущим approved Stage.** Источник истины по текущей
   стадии, её статусу и следующему шагу — `docs/PROJECT_STATE.md`. Краткое
   упоминание стадии в других документах (например, в `README.md`) допустимо, но
   не должно ему противоречить.
2. **Сначала читай документацию проекта:** `docs/PROJECT_STATE.md`, затем
   `ARCHITECTURE.md`, `docs/DOMAIN.md`, `docs/DEVELOPMENT.md`, `docs/TESTING.md`
   и план текущего Stage в `docs/plans/`.
3. **Не добавляй незапрошенные функции** — ни продуктовые, ни «попутные»
   инфраструктурные. Объём работ определяет план текущего Stage, не твои идеи.
4. **Не меняй product/domain поведение молча.** Изменение поведения = отдельный
   коммит + обновление соответствующего документа (`docs/PRODUCT.md`,
   `docs/DOMAIN.md`).
5. **Держи domain logic вне React-компонентов:** `src/domain` — чистый TypeScript
   без импортов react, expo, react-native, sqlite и UI. Направление зависимостей —
   `ARCHITECTURE.md`.
6. **Перед завершением задачи запускай и добивайся зелёного статуса:**
   `npm run lint && npm run typecheck && npm test`.
7. **Не ослабляй тесты ради зелёного CI:** не удаляй, не скипай и не смягчай
   проверки. Падение теста — повод чинить код (или явно обсудить сам тест), а не
   подгонять отчёт.
8. **Делай небольшие логические коммиты** в формате Conventional Commits
   (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`).
9. **Перед каждым коммитом проверяй `git diff`** — в коммит попадает только то,
   что задумано.
10. **Не переходи к следующему Stage самостоятельно:** следующий Stage стартует
    только после ревью и явного одобрения результатов текущего.
11. **Работай в отдельной ветке.** Под каждую задачу или логический этап — своя
    ветка от актуального `main` (именование — `docs/DEVELOPMENT.md`). В `main`
    изменения попадают только через Pull Request.
12. **Коммить и пушь в рабочую ветку разрешено** в рамках порученной задачи — без
    отдельной просьбы владельца. Пуш в `main` и merge в `main` агент не выполняет.
13. **Завершай задачу Pull Request'ом** в `main`; merge — только после независимого
    APPROVED и явного разрешения владельца.

## GitHub-first workflow (ветки, PR, merge)

Основной канал передачи изменений — **GitHub**; обмен патчами через AI Drive
(`docs/SYNC.md`) остаётся **резервным**.

1. **Ветка.** От актуального `main` создаётся рабочая ветка под задачу/этап.
2. **Коммиты.** Небольшие логические коммиты (Conventional Commits) в рабочую ветку;
   `git commit` и `git push` в рабочую ветку разрешены в рамках порученной задачи.
3. **Проверки перед ревью.** `npm run lint && npm run typecheck && npm test` (зелёные)
   плюс дополнительные проверки, предусмотренные планом задачи.
4. **Pull Request.** По завершении — PR в `main` с кратким описанием «что и почему».
5. **Ревью.** Независимый ревьюер проверяет PR, код, требования и результаты тестов.
6. **Правки.** Замечания исправляются в той же ветке; PR обновляется.
7. **Merge.** Только после независимого APPROVED и явного разрешения владельца.
   Агент merge не выполняет и следующий Stage самостоятельно не начинает.

## Ритуал завершения Stage

После завершения каждого Stage агент обязан:

1. остановить разработку — новые функции и следующий Stage не трогать;
2. выполнить `npm run lint && npm run typecheck && npm test` и добиться зелёного результата
   (плюс дополнительные проверки из плана Stage);
3. создать или обновить `REVIEW_REPORT.md` в корне проекта (структура — по утверждённому шаблону отчёта);
4. закоммитить результат в рабочей ветке и запушить её;
5. открыть Pull Request в `main` с кратким описанием изменений;
6. не выполнять merge в `main` и не переходить к следующему Stage самостоятельно;
7. дождаться независимого APPROVED и явного разрешения владельца.

## Передача файлов между пользователем и агентом

**Основной канал — GitHub.** Изменения передаются через рабочие ветки и Pull Request'ы
в репозитории проекта (см. раздел «GitHub-first workflow» и `docs/DEVELOPMENT.md`).
Коммит и пуш в рабочую ветку в рамках порученной задачи разрешены; merge в `main` —
только после независимого APPROVED и явного разрешения владельца.

**Резервный канал — обмен срезом через AI Drive** (`docs/SYNC.md`); используется, если
GitHub недоступен или владелец отдельно просит патч. Пользователь работает на ноутбуке
(Windows, `D:\Pr\orbit`).

- **Получить код (резерв):** `gsk aidrive download /orbit_sync/from_laptop/orbit_from_laptop.zip <куда>`
  вместе с `PUSH_INFO.txt` (там ветка, коммит и sha256 архива). Сверить sha256 перед распаковкой.
- **Отдать изменения (резерв):** `bash tools/sync/make_patch.sh -d <корень проекта> -v <ГГГГММДД-NN> -m "<что сделано>" <файлы…>`.
  Скрипт собирает архив с описанием и выкладывает его в `/orbit_sync/to_laptop`; пользователь
  забирает патч двойным щелчком по `orbit.cmd`, пункт 3.
- Патч выкладывать только на законченном и проверенном этапе. Правки пользователя не перезаписывать без его просьбы.
- Перед отправкой и приёмом по AI Drive напоминать пользователю включить VPN: без него его сеть
  отклоняет запросы к Genspark.
- В распакованном архиве `git status` может показывать все файлы изменёнными — это переводы строк
  Windows, а не правки. Смотреть реальные изменения: `git diff --ignore-cr-at-eol`.
  Новые файлы создавать с LF (добавить `.gitattributes` с `* text=auto eol=lf`).
- В архив не попадают `.env`, ключи, `node_modules`, базы — состав берётся по правилам `.gitignore`.

## Состояние проекта

Перед началом работы читать `docs/PROJECT_STATE.md` (проверенные факты и следующий шаг) и обновлять его
после каждого законченного этапа — только проверенными фактами.

## Экономичный режим работы

1. Контекст читать по карте, а не целиком: `docs/PROJECT_STATE.md` — первым файлом.
2. Один этап за окно; не начинать следующий, пока текущий не зелёный.
3. Тесты — точечно во время работы, полный прогон перед выкладкой патча.
4. Пушить в рабочую ветку только изменённые файлы; PR — с явным описанием изменений.
   Резервный патч (`make_patch.sh`) — только изменённые файлы (явный список путей).
5. Не пересказывать документы в ответах — ссылаться на разделы.
6. Короткие ответы: главное сверху, без повторов.
